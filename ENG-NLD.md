	<td>Overview</td>
	<td>This is a lightweight ASP.NET Core REST API built to process real-time trip updates for a public transit system. The core problem it solves is straightforward: operators report the actual departure and arrival times of their vehicles, and the system needs to determine whether each trip ran on time, early, or late, and keep a full audit trail of every decision made. The solution is deliberately scoped to that problem. There is no authentication, no message queue, no caching layer. The focus is on getting the domain logic right, structuring the code cleanly, and making the data flow easy to follow from an HTTP request all the way through to a persisted result.</td>
	<td>Dit is een lichtgewicht ASP.NET Core REST API, ontwikkeld voor het verwerken van realtime reisupdates voor een openbaarvervoersysteem. Het kernprobleem dat het oplost is eenvoudig: chauffeurs rapporteren de daadwerkelijke vertrek- en aankomsttijden van hun voertuigen, en het systeem moet bepalen of elke rit op tijd, te vroeg of te laat was, en een volledig auditspoor bijhouden van elke genomen beslissing. De oplossing is bewust beperkt tot dat probleem. Er is geen authenticatie, geen berichtenwachtrij en geen cachinglaag. De focus ligt op het correct implementeren van de domeinlogica, het overzichtelijk structureren van de code en het gemakkelijk traceerbaar maken van de gegevensstroom, van een HTTP-verzoek tot een opgeslagen resultaat.</td>
  </tr>
  <tr>
	<td>Architecture and Layering</td>
	<td>The solution is structured in three distinct layers that each have a single, clear responsibility. The controllers (`TripsController`, `UpdatesController`, and `UpdateLogsController`) are intentionally thin. They translate HTTP concerns (query parameters, request bodies, status codes) into service calls and return the result. No business logic lives there. The service layer is where all domain decisions happen: `TripService` owns the update processing pipeline and the punctuality calculation, while `UpdateLogService` owns the audit trail queries. Both services depend on `MockDatabase` for data access, but they never expose it; callers only ever receive DTOs. This separation means the persistence layer can be swapped out (for EF Core and a real database) without touching a single line of service or controller code.</td>
	<td>De oplossing is opgebouwd uit drie afzonderlijke lagen, elk met een duidelijke en eenduidige verantwoordelijkheid. De controllers (`TripsController`, `UpdatesController` en `UpdateLogsController`) zijn opzettelijk minimalistisch. Ze vertalen HTTP-aspecten (queryparameters, request bodies, statuscodes) naar serviceaanroepen en retourneren het resultaat. Er bevindt zich geen bedrijfslogica in deze laag. De servicelaag is waar alle domeinbeslissingen worden genomen: `TripService` beheert de updateverwerkingspipeline en de punctualiteitsberekening, terwijl `UpdateLogService` de auditlogquery's afhandelt. Beide services zijn afhankelijk van `MockDatabase` voor gegevenstoegang, maar ze stellen deze nooit beschikbaar; aanroepers ontvangen alleen DTO's. Deze scheiding betekent dat de persistentielaag kan worden vervangen (door EF Core en een echte database) zonder ook maar één regel service- of controllercode aan te raken.</td>
  </tr>

	<td>Domain Model and Status Calculation</td>
	<td>The domain model makes one important structural choice: `Trip` and `UpdateLog` are kept separate by design. A `Trip` holds the current state: the scheduled timetable and the latest punctuality status, overwritten on every update. An `UpdateLog` is an immutable audit record, one entry per update, never modified. This mirrors the real-world distinction between a live operations board (what is the status of this trip right now?) and a historical log (what happened to this trip over the course of the day?). The punctuality status itself is calculated in `TripService.DetermineStatus` using the industry-standard ±2-minute tolerance: departure and arrival deviations are each computed in minutes, averaged together, and then compared against the margin. Averaging the two smooths out cases where a vehicle departs late but recovers time en route, giving a single representative figure for the journey as a whole.</td>
	<td>Het domeinmodel maakt één belangrijke structurele keuze: `Trip` en `UpdateLog` worden bewust gescheiden gehouden. Een `Trip` bevat de huidige status: de geplande dienstregeling en de meest recente punctualiteitsstatus, die bij elke update wordt overschreven. Een `UpdateLog` is een onveranderlijk auditrecord, één item per update, dat nooit wordt gewijzigd. Dit weerspiegelt het onderscheid in de praktijk tussen een live operationeel overzicht (wat is de status van deze rit op dit moment?) en een historisch logboek (wat is er gedurende de dag met deze rit gebeurd?). De punctualiteitsstatus zelf wordt berekend in `TripService.DetermineStatus` met behulp van de industriestandaard tolerantie van ±2 minuten: afwijkingen bij vertrek en aankomst worden elk in minuten berekend, gemiddeld en vervolgens vergeleken met de marge. Door de twee te middelen worden gevallen waarin een voertuig te laat vertrekt maar onderweg tijd inhaalt, afgevlakt, waardoor een enkel representatief cijfer voor de hele reis wordt verkregen.</td>
  </tr>

	<td>Persistence and Batch Processing Pattern</td>
	<td>Persistence is handled by `MockDatabase`, a Singleton in-memory store that seeds realistic transit data on startup: two operators, three lines, five trips, all scheduled for tomorrow so the data always feels live. The Singleton lifetime is deliberate: every HTTP request reads and writes the same instance, which is what makes state changes visible across calls without any external infrastructure. The update endpoint accepts a batch of trip updates in a single request, which reflects how vehicle computers typically operate, reporting a run's worth of data in one transmission rather than one call per trip. Processing is done with a per-item try/catch so that one bad trip ID in a batch of ten does not abort the rest. The response always returns a full breakdown: total processed, success count, failure count, the audit log entries created for successes, and error messages for failures. This partial-success pattern gives the caller everything they need to know without requiring a follow-up query.</td>
	<td>De persistentie wordt afgehandeld door `MockDatabase`, een singleton in-memory opslag die bij het opstarten realistische reisgegevens genereert: twee operators, drie lijnen, vijf ritten, allemaal gepland voor morgen, zodat de gegevens altijd actueel aanvoelen. De singleton levensduur is bewust gekozen: elke HTTP-aanvraag leest en schrijft naar dezelfde instantie, waardoor statuswijzigingen zichtbaar zijn tussen verschillende aanroepen zonder externe infrastructuur. Het update-eindpunt accepteert een batch ritupdates in één enkele aanvraag, wat overeenkomt met de gebruikelijke werking van voertuigcomputers: de gegevens van een hele rit worden in één transmissie verzonden in plaats van één aanroep per rit. De verwerking gebeurt met een try/catch-blok per item, zodat één foutieve rit-ID in een batch van tien de rest niet afbreekt. Het antwoord retourneert altijd een volledig overzicht: totaal verwerkt, aantal succesvolle ritten, aantal mislukte ritten, de aangemaakte auditlogboekvermeldingen voor succesvolle ritten en foutmeldingen voor mislukte ritten. Dit patroon van gedeeltelijk succes geeft de aanroeper alle benodigde informatie zonder dat een vervolgquery nodig is.</td>
  </tr>

	<td>Testing Strategy</td>
	<td>The test suite covers the solution at two levels. The unit tests in `TripServiceTests` target the domain logic directly, specifically `DetermineStatus` and `ProcessUpdates`, using a real `MockDatabase` instance rather than mocks, since the database has no external dependencies and is fast to construct. Each test proves a specific domain behaviour: that 0-minute deviation returns OnTime, that +5 minutes returns Late, that an unknown trip ID produces a failure entry without aborting the batch, and that a valid update produces both a mutated trip status and a corresponding audit log entry. The integration tests in `IntegrationTests` boot the real application in-process using `WebApplicationFactory<Program>` and exercise the full HTTP stack (routing, model binding, the service layer, and the in-memory database) in a single test run with no network overhead. Together the two levels give confidence that both the domain rules and the end-to-end data flow behave correctly.</td>
	<td>De testsuite dekt de oplossing op twee niveaus. De unit tests in `TripServiceTests` richten zich direct op de domeinlogica, met name op `DetermineStatus` en `ProcessUpdates`, waarbij gebruik wordt gemaakt van een echte `MockDatabase`-instantie in plaats van mocks, omdat de database geen externe afhankelijkheden heeft en snel kan worden opgebouwd. Elke test bewijst een specifiek domeingedrag: dat een afwijking van 0 minuten OnTime retourneert, dat +5 minuten Late retourneert, dat een onbekende rit-ID een foutmelding genereert zonder de batch te annuleren, en dat een geldige update zowel een gewijzigde ritstatus als een bijbehorende auditlogboekvermelding oplevert. De integratietests in `IntegrationTests` starten de echte applicatie in-process met behulp van `WebApplicationFactory<Program>` en testen de volledige HTTP-stack (routing, modelbinding, de servicelaag en de in-memory database) in één testrun zonder netwerkoverhead. Samen bieden de twee niveaus de zekerheid dat zowel de domeinregels als de end-to-end dataflow correct functioneren.</td>
