# Trip Updates API - Solution Description

## Overview

This is a lightweight ASP.NET Core REST API built to process real-time trip updates for a public transit system. The core problem it solves is straightforward: operators report the actual departure and arrival times of their vehicles, and the system needs to determine whether each trip ran on time, early, or late, and keep a full audit trail of every decision made. The solution is deliberately scoped to that problem. There is no authentication, no message queue, no caching layer. The focus is on getting the domain logic right, structuring the code cleanly, and making the data flow easy to follow from an HTTP request all the way through to a persisted result.

## Architecture and Layering

The solution is structured in three distinct layers that each have a single, clear responsibility. The controllers (`TripsController`, `UpdatesController`, and `UpdateLogsController`) are intentionally thin. They translate HTTP concerns (query parameters, request bodies, status codes) into service calls and return the result. No business logic lives there. The service layer is where all domain decisions happen: `TripService` owns the update processing pipeline and the punctuality calculation, while `UpdateLogService` owns the audit trail queries. Both services depend on `MockDatabase` for data access, but they never expose it; callers only ever receive DTOs. This separation means the persistence layer can be swapped out (for EF Core and a real database) without touching a single line of service or controller code.

## Domain Model and the Status Calculation

The domain model makes one important structural choice: `Trip` and `UpdateLog` are kept separate by design. A `Trip` holds the current state: the scheduled timetable and the latest punctuality status, overwritten on every update. An `UpdateLog` is an immutable audit record, one entry per update, never modified. This mirrors the real-world distinction between a live operations board (what is the status of this trip right now?) and a historical log (what happened to this trip over the course of the day?). The punctuality status itself is calculated in `TripService.DetermineStatus` using the industry-standard ±2-minute tolerance: departure and arrival deviations are each computed in minutes, averaged together, and then compared against the margin. Averaging the two smooths out cases where a vehicle departs late but recovers time en route, giving a single representative figure for the journey as a whole.

## Persistence and the Batch Processing Pattern

Persistence is handled by `MockDatabase`, a Singleton in-memory store that seeds realistic transit data on startup: two operators, three lines, five trips, all scheduled for tomorrow so the data always feels live. The Singleton lifetime is deliberate: every HTTP request reads and writes the same instance, which is what makes state changes visible across calls without any external infrastructure. The update endpoint accepts a batch of trip updates in a single request, which reflects how vehicle computers typically operate, reporting a run's worth of data in one transmission rather than one call per trip. Processing is done with a per-item try/catch so that one bad trip ID in a batch of ten does not abort the rest. The response always returns a full breakdown: total processed, success count, failure count, the audit log entries created for successes, and error messages for failures. This partial-success pattern gives the caller everything they need to know without requiring a follow-up query.

## Testing Strategy

The test suite covers the solution at two levels. The unit tests in `TripServiceTests` target the domain logic directly, specifically `DetermineStatus` and `ProcessUpdates`, using a real `MockDatabase` instance rather than mocks, since the database has no external dependencies and is fast to construct. Each test proves a specific domain behaviour: that 0-minute deviation returns OnTime, that +5 minutes returns Late, that an unknown trip ID produces a failure entry without aborting the batch, and that a valid update produces both a mutated trip status and a corresponding audit log entry. The integration tests in `IntegrationTests` boot the real application in-process using `WebApplicationFactory<Program>` and exercise the full HTTP stack (routing, model binding, the service layer, and the in-memory database) in a single test run with no network overhead. Together the two levels give confidence that both the domain rules and the end-to-end data flow behave correctly.
